# ResQNet WebSocket Protocol

The ResQNet backend provides a real-time WebSocket event stream for the application layer. This stream allows the frontend to monitor and visualize network state, topology changes, and packet routing in real-time.

## Connection

**Endpoint:** `ws://<host>:<port>/api/ws/simulation`

No authentication is currently required. As soon as a client connects, the server will emit an `INITIAL_STATE` event containing the current topology and node statuses.

## Event Structure

Every event sent to the client follows a standard JSON envelope:

```json
{
  "event_id": "uuid-string",
  "type": "EVENT_TYPE",
  "timestamp": "ISO-8601-timestamp",
  "data": { ... }
}
```

## Standard Event Types

The backend exposes **exactly** the following standardized WebSocket event types. Any future events will be added to this contract explicitly.

### Network Lifecycle
* `INITIAL_STATE` - Sent immediately upon WebSocket connection. Contains the current network nodes and links.
* `SIMULATION_RESET` - Sent when the simulation is reset to its default state. (Note: `SIMULATION_STARTED` is currently unimplemented as the simulation is implicitly started when packets are routed).

### Node and Link Failures
* `NODE_FAILED` - A node has gone offline. `data` contains `node_id`.
* `NODE_RECOVERED` - A node has come back online. `data` contains `node_id`.
* `LINK_FAILED` - A link between two nodes has failed. `data` contains `node_a_id` and `node_b_id`.
* `LINK_RECOVERED` - A link between two nodes is restored. `data` contains `node_a_id` and `node_b_id`.

### AODV Route Discovery (Control Plane)
These events trace the path of AODV control packets (RREQ, RREP, RERR). For all packet-related events, `data` includes standard packet metadata such as `packet_id`, `source_id`, `destination_id`, and `sender_id`.

* `RREQ_GENERATED` - An RREQ was created by a source node.
* `RREQ_FORWARDED` - An RREQ was broadcast/forwarded by an intermediate node. `data` includes `from_node` and `to_node`.
* `RREQ_RECEIVED` - An RREQ successfully reached the destination node.
* `RREP_GENERATED` - An RREP was created by the destination node.
* `RREP_FORWARDED` - An RREP was unicast back along the reverse route. `data` includes `from_node` and `to_node`.
* `RREP_RECEIVED` - An RREP successfully reached the original source node.
* `ROUTE_DISCOVERY_COMPLETED` - A full AODV route discovery cycle successfully completed.
* `RERR_GENERATED` - An RERR was generated due to a broken link.
* `RERR_FORWARDED` - An RERR was propagated to affected upstream nodes. `data` includes `from_node` and `to_node`.
* `ROUTE_INVALIDATED` - A routing table entry was invalidated due to an RERR or link failure.

### Data Forwarding (Data Plane)
These events trace the path of actual application DATA packets.

* `DATA_CREATED` - A new DATA packet was generated at the source.
* `DATA_FORWARDED` - A DATA packet was forwarded to the next hop. `data` includes `from_node` and `to_node`.
* `DATA_DELIVERED` - A DATA packet successfully reached its final destination.
* `DATA_DROPPED` - A DATA packet was dropped (e.g., no route available).

## Important Guarantees

1. **`sender_id` Guarantee:** Every packet-related event cleanly exposes `sender_id` in the `data` payload. This explicitly identifies the *previous hop* the packet just came from, which is critical for frontend animation paths.
2. **Chronological Ordering:** Events are guaranteed to arrive over the WebSocket in the exact chronological order they were generated by the simulation engine (e.g., `RREQ_GENERATED` -> `RREQ_FORWARDED` -> `RREQ_RECEIVED`).
3. **Resilience:** The broadcaster handles slow or disconnected clients gracefully without crashing the server or lagging the simulation.
